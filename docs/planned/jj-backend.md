# 計画中の機能: バージョン管理を git から jj (Jujutsu) へ

- 日付: 2026-09-30
- 状態: 保留 (検討のみ・未検証)
- 対象: [jj-vcs/jj](https://github.com/jj-vcs/jj)
- きっかけ: Stage 8 (ブランチ別チャット) と 8d (オーケストレータに書き込みを許す・ブランチ名変更への追従) の検討中に、
  「今回の用途だと git より jj の方が優れているのでは」という問い。

## jj の方が優れている点 (Yhtye の設計との関係)

| 今の弱点 (git) | jj では |
|---|---|
| オーケストレータが小さな変更をコミットし忘れると、未コミットの変更が残りグループのマージが merge_blocked になる (8d) | 作業コピー自体がコミット (自動スナップショット)。「未コミットの変更」という状態が無い |
| マージの衝突で失敗し、`merge_conflict` の help → 対処の流れが要る | 衝突をコミットの中に持てる (first-class conflicts)。マージは失敗せず、解決は後からできる |
| ブランチ名の変更・checkout を検出して追従する処理が要る (8d) | change ID は書き換えても変わらない。チャットを change ID / bookmark に紐づければ追従処理が減る |
| エージェントが壊したときの復旧 | `jj op log` / `jj undo` で操作単位で戻せる |
| 複数エージェントの同時操作 | ロック無しで並行した操作を記録し、自動で統合する |

## 保留の理由

- **エージェントが git を前提に作業する。** Claude Code / Codex / OpenCode は `git status` / `git commit` / `git diff` を使う。
  jj の追加ワークスペース (`jj workspace add`) には `.git` が無く、git コマンドや git を読むツールが動かない可能性がある
  (**未検証**。最新版で確認が要る)。これが通らないと実装者のワークツリーを jj にできない。
- **利用者の負担。** 公開アプリなので、jj の導入や colocated リポジトリ (`.jj` + `.git`) への移行を求めることになる。
  PR・GitHub 連携は git 側に残る。
- **作り直しが大きい。** git 層 (`crates/yhtye-core/src/git/`: ワークツリー、マージ、ブランチ、グラフ) は git CLI で書いてある。
  `jj-lib` (Rust) は API がまだ安定していない。
- **当面の問題は git のままでほぼ片付く。** 未コミットの変更は「マージ前に変更なし」の検査とプロンプトで、
  ブランチ名の変更は 8d の検出と追従で扱える。

## 再開するときに最初に確かめること (検証の順)

1. colocated リポジトリの**追加ワークスペース**で、Claude Code (Haiku) が普通に作業・コミットできるか
   (git コマンドが動くか。動かないなら jj コマンドを使わせられるか)。
2. 衝突を含むマージを、グループの流れ (`merge_conflict` help → modify_steps → resume) にどう載せるか。
3. 利用者のリポジトリを変えずに (`.jj` を置かずに) 使えるか。Yhtye 専用の場所に jj の repo を持ち、git と同期する案も含めて。
4. 1 が通れば、git 層を `GitService` の背後で jj に差し替える案 (UI・ドメインはブランチ = bookmark として維持) を設計する。

検証時点では jj はこの環境に入っていない (`jj: command not found`)。
