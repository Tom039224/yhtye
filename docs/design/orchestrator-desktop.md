# Yhtye — Orchestrator Desktop 画面仕様

Claude Design の `Orchestrator Desktop.dc.html` を読み解いて起こした仕様。
色・書体・アニメーションの値は [`tokens.md`](tokens.md) に分けてある。

> このデザインは**単一のモック画面**であり、網羅的な仕様書ではない。
> ここに書いていないもの (設定画面、エラー画面、空状態の大半、オンボーディング) は
> **デザインに存在しない**。実装時に発明が必要な箇所は「未定義」として明示してある。

## 1. 何のアプリか

複数のコーディングエージェントを**オーケストレータ経由で**動かすデスクトップクライアント。
ユーザーはエージェント個体に直接指示せず、オーケストレータに自然文で依頼する。
オーケストレータが作業をタスクに割り、サブエージェントへ配り、結果をまとめて返す。

モックが描いている具体的な筋書き:

1. ユーザー「チェックアウトのバリデーションを整理したい。まず現状を調べて、必要ならタスクに割って進めて。」
2. オーケストレータが 4 ファイルの重複を検出し、**グループタスク**「checkout バリデーション統合」として
   T-108 / T-109 / T-110 に分割、agent-a / agent-b / agent-c へ配る
3. T-110 が API スキーマの v2/v3 混在で詰まる。**グループ完了を待たずに**オーケストレータへ報告が上がる
4. オーケストレータが agent-c を待機させ、v3 へ寄せる修正を**自分で**実行中

この 3→4 の流れがこのアプリの主張そのもの。「異常はグループの完了を待たずに上がってくる」
「オーケストレータは配るだけでなく自分でも手を動かす」の 2 点を UI が支えている。

## 3. 各部の仕様

### 3.1 タイトルバー

- 左: ワードマーク「Yhtye」(Space Grotesk 600 / 14px / `letter-spacing:.1em`)
- 右: **現在ブランチのピル** — 緑ドット + `feat/checkout-refactor` (モノスペース 11px)、枠 `--border-card`

未定義: ウィンドウ操作ボタン (最小化・最大化・閉じる) がデザインに無い。
OS 標準のデコレーションを使うか、`decorations:false` にして自前で描くかは未決。

### 3.2 アイコンレール

2 つのビューを切り替えるだけ。

| アイコン | ビュー | ツールチップ |
|---|---|---|
| `</>` | `work` | コーディング |
| `▤` | `runs` | 履歴 |

アクティブ表現は 3 点セット: 地 `--surface-chip` / 文字 `--accent` /
**左外側に 2×16px の琥珀のマーカーバー** (`left:-8px; top:6px`)。
非アクティブは文字 `--text-dim` + ホバーで地 `--surface-hover` / 文字 `--text-tertiary`。

`runs` ビューの中身は**空状態「現状は何もありません」のみ**。履歴画面は未設計。

### 3.3 プロジェクト / ブランチ (work ビュー)

**PROJECTS** — 各行はリング + 名前。リングの形が状態を表す:

| リング | 状態 |
|---|---|
| 上辺だけ濃い緑の円が回転 (`yspin`) | 実行中 |
| 緑の輪郭 (静止) | 待機中・接続済み |
| グレーの輪郭 `#4a453f` | 停止・未接続 |

**BRANCHES** — 6px のドット + ブランチ名 (モノスペース 11.5px)。
現在ブランチは緑ドット + 地 `--surface-selected`、他は `#403c37` のドット。

**フッタ** — リモートホストの状態。緑ドット + `remote host 1` + `last sync 4s`。
`<br>` が残っているので複数ホストを縦に並べる想定と読める。

未定義: プロジェクト/ブランチの追加・削除 UI が無い。ブランチ切替の確認フローも無い。

### 3.4 オーケストレータ会話

ヘッダは `orchestrator` の一語のみ。

**発話** — ラベル行 (`YOU · 14:02` / `ORCHESTRATOR · 14:19`) + 本文。
ラベルは大文字モノスペース 10px、オーケストレータ側だけ琥珀。本文は日本語 13px / `line-height:1.75`。

**発話に埋め込まれる部品** (3 種類がモックに出ている):

1. **グループタスクカード** — ヘッダ `GROUP TASK · <グループ名>`、
   本体は連番 + タスク ID + タスク名の行。連番は `--text-faintest` で沈める
2. **アクションボタン列** — 「対処の内容を見る」「差分を見る」。枠線ボタン、
   ホバーで文字 `--text-body` / 枠 `--border-hover`。**Stage 7a でユーザーが決定: 実装しない (ボタンを出さない)**
3. **本文中の強調** — `v3 へ寄せる` のように方針の核だけ `--accent-strong` で色を持つ

**グループ待機バナー** — 会話末尾に破線枠で常駐。
`グループ「…」の全タスク完了まで待機中 — 1/3 完了 · 1 件 対処中`。
完了数と対処中件数を持つ。グループが走っている間だけ出る。

**コンポーザ** — 枠付きの箱。上段がプレースホルダ「オーケストレータに指示する…」、
下段が横並びのチップ列:

- **メンションチップ** — `@<タスク名> ×`。クリックで消える。最大幅 180px で省略。
  タスクカードの `@` ボタンから積まれる
- **モードピル** `orchestrate` — 地 `--surface-chip-dim`。他のモードは未定義
- 右端に `⏎ 送信`

### 3.5 タスク列

ヘッダ: `tasks` / グループ名チップ / `1/3 完了` / 右端に `subagents 4`。

**タスクカード**の構成 (上から):

1. ヘッダ行 — ステータスバッジ / タスク ID / タスク名 / 右端にアイコンボタン 2 つ
2. 進捗バー (稼働中のみ) — 高さ 2px。地 `--border` の上に色付きバー、
   さらに `ysheen` で光が走る
3. 対処中のみ: 状況説明の日本語文
4. ログ行 (`showTaskLog`) — モノスペース 10.5px、`<br>` 区切りの 2 行
5. フッタ — `agent-a · 6m` (担当エージェントと経過時間)

**ステータスと見え方:**

| ステータス | バッジのドット | 進捗バー | カード |
|---|---|---|---|
| 実装中 | 青・`ypulse` | あり (62%) | 通常 |
| レビュー中 | 紫・`ypulse` | あり (88%) | 通常 |
| 対処中 | **ドット無し** | **無し** | **全体が赤橙に染まる** |
| 完了 | ドット無し | 無し | 沈んだ地・枠、タスク名も `--text-quaternary` |

**アイコンボタン:**

| ボタン | ツールチップ | 挙動 |
|---|---|---|
| `@` | オーケストレータへ引用 | そのタスク名をコンポーザのメンションチップに積む |
| ■ (8×8 の角丸四角) | エージェントを停止 | 担当エージェントを止める |

**完了タスクには停止ボタンが無い** (`@` のみ)。

**完了タスクの補足行** — `同グループの他タスク完了を待機 — 送信保留`。
終わっていても、グループが揃うまで結果が出ていかないことを示す。
「対処中」の `agent-c 待機 · orchestrator 対処中` も同じ系統のメタ行。

### 3.6 git グラフ

ヘッダ: `git` / `feat/checkout-refactor ← main` / 右端に `graph`。

レーンは**絶対配置の縦線と円**で描かれている。

| レーン x | 色 | 意味 |
|---|---|---|
| 19px | `#3a3733` | main |
| 41px | `oklch(0.55 0.09 250)` | agent-a の枝 |
| 63px | `oklch(0.5 0.1 30)` | T-110 (対処中) の枝 |

分岐は**長さ 18px / `rotate(-38deg)` の斜線**で表す。
コミット行は高さ 28px、`padding-left:86px` でテキストがレーンを避ける。

各行: 円 (`11×11`, 枠 2px, 地はパネル色) / sha (モノスペース 10.5px) / メッセージ / 右端バッジ。
バッジは `main` `agent-a` `review` `対処中` の 4 種がモックに出ている。
**バッジがタスクのステータス色と対応している** — git 上のどのコミットがどのエージェントの
どの状態の仕事かが一目で分かる、というのがこのパネルの狙い。

最下行は HEAD で、sha の代わりに `HEAD`、メッセージが `グループ作業中`、塗りつぶしの円。

未定義: コミットのクリック、差分表示、マージ/プッシュ操作。

### 3.7 ステータスバー

- 左: `claude max` (プラン名)
- 右: 2 つの使用量メーター
  - `5h` — 幅 46px / 高さ 3px のバー、94%、橙、`(3h 35m)` 残り
  - `week` — 40%、緑、`(2d 4h)`
  - 間に 1×12px の区切り線

## 4. 状態とインタラクション

デザイン原本の `DCLogic` が持っている状態:

```js
state = { view: "work", mentions: ["重複バリデーションの棚卸し"], stopped: [] }
```

| 操作 | 結果 |
|---|---|
| アイコンレールの `</>` / `▤` | `view` を `work` / `runs` に切替 |
| タスクカードの `@` | そのタスク名を `mentions` に追加 (重複は積まない) |
| メンションチップのクリック | そのチップを `mentions` から除去 |
| タスクカードの ■ | タスク ID を `stopped` に追加 (重複は積まない) |

**注意** — `stopped` は状態に積まれるだけで、モックでは**見た目に何も反映されていない**。
停止後のカードの表現は未設計。実装時に決める必要がある。

`props` の `showGit` / `showTaskLog` / `showGroupBanner` は Claude Design の
プレビュートグル。**アプリの設定ではない。**

## 5. デザインから読めるドメインモデル

画面に出ている情報だけから起こしたもの。永続化やプロトコルの設計はこれとは別に必要。

```ts
type ProjectStatus = "running" | "ready" | "stopped";
type TaskStatus    = "implementing" | "reviewing" | "handling" | "done";
//                    実装中          レビュー中    対処中       完了

interface Project  { id: string; name: string; status: ProjectStatus }
interface Branch   { name: string; isCurrent: boolean; isActive: boolean }
interface RemoteHost { id: string; label: string; online: boolean; lastSyncSeconds: number }

interface Agent    { id: string; /* "agent-a" */ state: "working" | "waiting" | "idle" }

interface Task {
  id: string;              // "T-108"
  title: string;
  status: TaskStatus;
  progress?: number;       // 0..1。稼働中のみ
  agentId?: string;
  elapsedMinutes: number;
  log: string[];           // モックは 2 行
  note?: string;           // 対処中の説明文
  metaLine?: string;       // "同グループの他タスク完了を待機 — 送信保留"
  groupId?: string;
}

interface GroupTask {
  id: string;
  title: string;           // "checkout バリデーション統合"
  taskIds: string[];
  completed: number;
  total: number;
  handlingCount: number;   // 「1 件 対処中」
}

type MessageAttachment =
  | { kind: "groupTask"; group: GroupTask }
  | { kind: "actions"; actions: { label: string; action: string }[] };

interface Message {
  id: string;
  role: "user" | "orchestrator";
  at: string;              // "14:02"
  body: string;            // 一部を --accent-strong で強調しうる
  attachments: MessageAttachment[];
}

interface Commit {
  sha: string | "HEAD";
  message: string;
  lane: number;            // 0 = main, 1.. = 枝
  parentLane?: number;     // 分岐の斜線を引く先
  badge?: { label: string; tone: "neutral" | TaskStatus };
}

interface Quota { window: "5h" | "week"; percent: number; remainingLabel: string }
```

## 6. Tauri の境界 (これから決めること)

デザインには現れないが、実装で最初に決まっていないと進めない線。**まだ未決**。

ハーネスとの接続方式・対象ハーネス・オーケストレーションのモデル
(グループ/タスク/エージェントの機能設計) は [`docs/architecture/`](../architecture/) に
別途まとめた。Rust / フロントエンドの境界は
[`docs/architecture/core-design.md`](../architecture/core-design.md) で確定しており、
そちらが優先する。以下は画面設計から読んだ当初の想定として残す。

フロントエンド (React) が持つべきもの:
- 描画と、`view` / `mentions` / スクロール位置といった純粋な UI 状態のみ

Rust 側が持つべきもの (想定):
- git 操作 (グラフ構築、ブランチ列挙、差分) — `git2` か `gix`
- ACP クライアントとしてのハーネスプロセスの起動・停止・セッション管理
  ([`docs/architecture/acp-harnesses.md`](../architecture/acp-harnesses.md))
- リモートホストとの同期
- タスク / グループ / 会話の永続化
- 使用量 (quota) の取得

フロントへの流し込みは Tauri の `emit` によるイベント購読が中心になる想定
(タスク進捗・ログ・git 更新はすべてプッシュ型)。コマンド一覧は実装着手時に別途起こす。

## 8. 実装との対応 (Stage 6a)

Stage 6a でこのレイアウトを `src/ui/` に適用した。**画面の要素はすべてコアの実データから描く**。
データの無いものは値を作らず、空 / プレースホルダを出す。スクリーンショット: [`docs/e2e/stage6a/`](../e2e/stage6a/)。

| デザインの要素 | 実装 (データ源) |
|---|---|
| タイトルバーのブランチピル | プロジェクトで checkout されているブランチ (`GetGitOverview.head`) |
| アイコンレール | `work` / `runs` の切替。`runs` はデザインどおり「現状は何もありません」(履歴画面は保留、Stage 7a) |
| PROJECTS のリング | 停止 = 開いていない / 待機中 = 開いている / 実行中 (回転) = 開いているプロジェクトのセッションがターン中 |
| (追加) リポジトリを開く欄 | PROJECTS の下の小さな入力欄 (デザインに追加 UI が無いため) |
| BRANCHES | ローカルブランチ一覧 (`GetGitOverview.branches`)。現在ブランチが緑 + 選択地 |
| フッタ「remote host / last sync」 | **ローカルのコアへの接続** (`local core · websocket` / `app`) と最後にイベントが届いてからの秒数。リモートホストは未対応 |
| 会話の発話 | `YOU` / `ORCHESTRATOR` ラベル + 時刻。ツール呼び出し・思考・受信箱の通知は控えめなモノスペース行 (Stage 4 と同じ情報) |
| GROUP TASK カード | `group_created` イベントの位置に出し、中身 (連番 + タスク ID + 名前) は現在の状態から読む |
| アクションボタン列 (対処の内容を見る / 差分を見る) | **出さない** (Stage 7a でユーザーが決定)。タスク名のクリックでエージェント出力を見られる |
| 本文中の強調 (`--accent-strong`) | **6b**: エージェントの発話 (会話・エージェント出力、ストリーミング中も) を Markdown で描画 (`src/ui/Markdown.tsx`、react-markdown + remark-gfm)。`**太字**` が `--accent-strong`。生 HTML は描画しない・リンクは http(s)/mailto のみ外部で開く・画像は読み込まず alt 表示。ユーザーの発話・思考・通知はプレーンのまま |
| グループ待機バナー | active / finishing のグループがある間だけ。`x/y 完了 · n 件 対処中` は状態から計算。**7a**: 全タスクが落ち着いたのにグループが active (オーケストレータの `finish_group` 待ち) なら「全タスクが完了 — オーケストレータがグループを完了 (マージ) するのを待っています」、finishing は「base ブランチへマージ中」 |
| コンポーザ | 入力欄 + メンションチップ + `orchestrate` ピル + `⏎ 送信`。ターン中は「ターンを中止」 (7d: ⚙ は左端のバーへ移した) |
